# Code Search MCP Server（Java版）— 要件書

本書は、Git リポジトリ上のソースコードを検索するための
Model Context Protocol（MCP）サーバーの Java 実装の要件を定義する。

本実装は、Python リファレンス実装
（[codesearch-mcp-python](https://github.com/nncdevel-io/codesearch-mcp-python)）
の **外部仕様を完全に踏襲した移植版**である。クライアントから観察可能な
振る舞い（ツール入出力、エラーモデル、Git URL、設定ファイルスキーマ）は
リファレンス実装と同一に保つ。変わるのは内部実装言語と実行形態のみである。

## 1. 目的と背景

### 1.1 目的

チャットアプリケーションのエージェントから利用される、Git 管理された
ソースコードに対する検索基盤を MCP サーバーとして提供する。

エージェントは本サーバーが公開するツールを通じて、ソースコード全体に
対するパターン検索、ファイル名による検索、ディレクトリ階層の俯瞰、
ファイル内容の読み取りを行い、ユーザーへの回答に必要な実装上の根拠
（ファイルパス、行番号、Git URL）を取得する。

### 1.2 背景

ベクトル検索（チャンク化＋埋め込み＋類似度検索）は、関数・クラス境界の
断裂、再インデックスの運用負荷、引用の曖昧さという問題を抱える。本サーバーは
ベクトル検索を採らず、「人間が `ripgrep` と `git ls-files` でコードを追う
手順」をエージェントにそのまま提供する方針を踏襲する。

詳細な背景・ツール設計の参考仕様はリファレンス実装の要件書に準ずる。

### 1.3 Java 版を新規に作る目的

Python 版と同一の外部仕様を保ちつつ、JVM エコシステムへ展開することを
目的とする。具体的には次の2系統の利用形態を同時に満たす。

- **単独利用**: スタンドアロンの実行可能成果物として、CLI から起動する
  （Python 版と同等の運用）。
- **Spring Boot 統合**: 既存の Spring Boot アプリケーションへ組み込み、
  同一の検索ツール群を MCP サーバーとして公開する。

この2系統を破綻なく両立させるため、中核ロジックはフレームワーク非依存と
し、トランスポート／ランタイムを差し替え可能にする（詳細は設計書）。

## 2. スコープ

### 2.1 やること

- Git リポジトリの定期的な取得（clone および pull）
- 指定ブランチに限定したソースコードの提供
- ファイル内容のパターン検索ツールの MCP 公開（`search_code`）
- ファイル名パターンによる検索ツールの MCP 公開（`list_files`）
- ディレクトリ階層を俯瞰するツールの MCP 公開（`list_tree`）
- 行範囲指定でのファイル読み取りツールの MCP 公開（`read_file`）
- 設定済みリポジトリのカタログを返す discovery ツールの公開
  （`list_repositories`）
- 設定済みリポジトリの MCP Resource 広告（`codesearch://repo/{id}`）
- 検索結果における Git ホスティングサービス上の URL の付与
- 複数リポジトリの同時取り扱い
- stdio と Streamable HTTP の両トランスポート対応
- **単独利用（CLI ＋ 組込みサーブレットコンテナー）の提供**
- **Spring Boot 統合（スターターによる自動構成）の提供**

### 2.2 やらないこと

- ベクトル検索および埋め込みインデックスの構築
- 自然言語クエリの解釈（クライアント側 LLM の責務とする）
- ソースコードの書き換え、Git への push
- ユーザーごとの権限管理（本サーバーは単一の権限で動作する）
- チャット UI そのものの提供
- ドキュメント検索やナレッジベース検索
- 画像、PDF、Jupyter Notebook など非テキストファイルの解釈
- リファレンス実装に存在しない新規ツールの追加（パリティを優先する）

## 3. 想定利用シナリオ

### 3.1 主要なシナリオ

エンドユーザーがチャットアプリに対し「`StreamingResponseBuilder`
クラスがどう実装されているか」と問い合わせる。クライアント側の
エージェント（LLM）は次の順序でツールを呼び出す。

1. `list_tree` でリポジトリ全体の構造を俯瞰する
2. `search_code` で対象を検索し、ファイルパスと行番号を取得する
3. 必要に応じて `list_files` で周辺のファイル構成を確認する
4. `read_file` で該当範囲を読み取り、実装内容を取得する

エージェントは結果を統合し、回答本文に Git URL（行番号アンカー付き）を
引用として埋め込む。

### 3.2 副次的なシナリオ

- 特定のリポジトリのみを対象にした検索
- 特定のファイル拡張子に絞った検索
- 初見リポジトリにおけるディレクトリ階層の俯瞰
- 既存 Spring Boot アプリへ組み込んだ状態での同一ツール提供

## 4. 機能要件

機能要件の詳細（各ツールの入力・出力・挙動）は、リファレンス実装の
外部仕様を踏襲する。本書では要点のみを示し、入出力スキーマの厳密な定義は
仕様書（`docs/devel/specs/spec.md`）に置く。

### 4.1 検索ツール（search_code）

- 目的: ファイル内容のパターン検索
- バックエンド: `ripgrep`（`rg`）
- 入力: `pattern`（必須）、`repository`（必須）、`path`、`glob`、`type`、
  `case_sensitive`、`output_mode`（`content`／`files_with_matches`／
  `count`）、`context_before`、`context_after`、`max_results`
- 出力: ヒットごとの `repository`／`file_path`／`line_number`／
  `line_content`／`git_url`、および `truncated`／`total_matches`
- 挙動: `.gitignore` 記載ファイル・バイナリ・隠しファイルを除外する

### 4.2 ファイル名検索ツール（list_files）

- 目的: グロブパターンに一致するファイルの列挙
- バックエンド: `ripgrep --files`
- 入力: `repository`（必須）、`pattern`（必須）、`path`、`max_results`
- 出力: ファイルごとの `repository`／`file_path`／`last_modified`／
  `git_url`、結果は `last_modified` の降順
- 挙動: `.gitignore` 対象・バイナリも結果に含める

### 4.3 ディレクトリ階層ツール（list_tree）

- 目的: ディレクトリ階層の俯瞰
- バックエンド: `git ls-files`（ツリー整形はサーバー内で実施）
- 入力: `repository`（必須）、`path`、`max_depth`、`show_files`、
  `max_entries`
- 出力: `repository`／`root_path`／`tree`（ASCII アート）／`truncated`／
  `entry_count`
- 挙動: Git 追跡ファイルのみを対象とする

### 4.4 ファイル読み取りツール（read_file）

- 目的: 指定ファイルの指定行範囲を行番号付きで読み取る
- バックエンド: なし（JVM 標準のファイル入出力で実装）
- 入力: `repository`（必須）、`file_path`（必須）、`start_line`、
  `num_lines`
- 出力: `repository`／`file_path`／`start_line`／`end_line`／
  `total_lines`／`content`（行番号タブ整形）／`git_url`
- 挙動: サイズ超過は `FILE_TOO_LARGE`、バイナリは `FILE_BINARY` を返す

`read_file` のみ外部コマンドを使わない理由はリファレンス実装と同じで、
本ツールの処理規模ではプロセス起動コストが読み取り処理を上回るためである。

### 4.5 リポジトリカタログツール（list_repositories）

- 目的: 設定済みリポジトリのカタログを LLM に届ける discovery
- 入力: なし
- 出力: リポジトリごとの `id`／`branch`／`hosting`／`hosting_base_url`／
  `exclude_paths`／`refresh_interval_seconds`／`description`／`status`

### 4.6 Git 同期

- 初期取得: 起動時、未取得のリポジトリを指定ブランチで `git clone` する
- 定期更新: スケジューラーが設定間隔で `git fetch` ＋
  `git reset --hard origin/<branch>` を実行する（既定間隔は15分）
- ブランチ制約: 設定で指定したブランチのみを参照する
- 同期はリクエストパスから完全に分離する（後述の非機能要件 5.1／5.2）

### 4.7 設定管理

- リポジトリ定義は `repos.toml` に記述する（TOML 形式を維持する）
- 認証情報は `secrets.toml` に分離し、パーミッションは600とする
- 起動パラメーターは `server.toml` に切り出せる
- 設定値の優先順位は CLI ＞ 環境変数 ＞ 設定ファイル ＞ 組込みデフォルト

### 4.8 Git URL の生成

- 検索・読み取り結果に Git ホスティング上の URL（行番号アンカー付き）を
  付与する
- 対応ホスティング: GitHub／GitLab／Bitbucket／Gitea
- 範囲指定時は各ホスティングの記法で範囲アンカーを生成する

## 5. 非機能要件

### 5.1 性能

- `search_code` は100万行規模でも95パーセンタイルで2秒以内に応答する
- `read_file` は500ミリ秒以内に応答する
- `list_files` は1秒以内に応答する
- `list_tree` は1秒以内に応答する

### 5.2 可用性

- 再起動後、Git 同期を待たず既存ワークスペースで即座に検索を提供する
- 個別リポジトリの取得失敗が他リポジトリの利用可能性に影響しない

### 5.3 信頼性

- Git 同期失敗はログに記録し、次回スケジュール時に再試行する
- 検索ツール失敗時は原因を判別可能なエラー応答を返す

### 5.4 セキュリティ

- ローカルワークスペース外へのパストラバーサルを禁止する
  （`..`・絶対パスの拒否、realpath による封じ込め）
- 設定で宣言されていないリポジトリへのアクセスを拒否する
- 秘密情報をログに出力しない
- 同期処理は最小権限の認証情報で行う（push 権限を要求しない）
- 外部コマンドはシェルを経由せず起動し、コマンドインジェクションを防ぐ
- MCP クライアントは内部ネットワークまたは認証済み経路からの接続に
  限定する想定とする（サーバー自体の認証機構は要件に含まない）

### 5.5 リソース制約

- `read_file` の最大読み取り行数は2000行、サイズ上限は10MB
- `search_code` の最大ヒット数は500件
- `list_files` の最大返却ファイル数は500件
- `list_tree` の最大エントリー数は1000件、最大深さは5

### 5.6 運用性

- 起動・定期同期・ツール呼び出しの主要イベントを構造化ログとして出力する
- 各リポジトリの最終同期時刻と同期結果を確認できる手段を提供する
- ログレベルが `DEBUG` のときに限り、MCP の JSON-RPC メッセージ全文を
  構造化ログとして出力できる（既定の `INFO` では出力しない）
- 上記デバッグログでも秘密情報の秘匿（5.4）を維持する

### 5.7 移植の同等性

- クライアントから観察可能な振る舞いはリファレンス実装と同一とする
- 同一の `repos.toml`／`secrets.toml`／`server.toml` が両実装で動作する
  （設定互換性を維持する）

## 6. 制約と前提

### 6.1 実装言語と動作環境

- 実装言語は Java とし、ターゲットは Java 21（LTS）とする
- ビルドツールは Maven とし、マルチモジュール構成とする
- 並行処理は Virtual Threads を基本とする
- 動作環境は Linux または macOS とする

### 6.2 成果物の形態

本実装は次の3モジュールで構成し、利用形態に応じて成果物を選べる。

| モジュール | 役割 |
| --- | --- |
| `codesearch-mcp-core` | フレームワーク非依存の中核（ツール・リソース・ドメインロジック） |
| `codesearch-mcp-standalone` | 単独利用。CLI ＋ 組込みサーブレットコンテナー ＋ stdio ランナー |
| `codesearch-mcp-spring-boot-starter` | Spring Boot 統合。自動構成で core を MCP サーバーへ登録 |

`codesearch-mcp-core` は Spring・サーブレットコンテナー・CLI のいずれにも
依存してはならない。

### 6.3 外部依存

#### 6.3.1 必須コマンド

サーバーから以下のバイナリーが呼び出し可能であること。

| コマンド | 用途 |
| --- | --- |
| `git` | リポジトリ取得・更新、`list_tree` のファイル列挙 |
| `ripgrep`（`rg`） | `search_code`、`list_files` |

`read_file` は外部コマンドを使わず JVM 標準ライブラリーで実装する。
バックエンドコマンドの選定根拠（速度優先）はリファレンス実装の要件書に
準ずる。

#### 6.3.2 必須ライブラリー

| 種別 | ライブラリー（候補） | 用途 |
| --- | --- | --- |
| MCP フレームワーク | 公式 MCP Java SDK（`io.modelcontextprotocol.sdk:mcp`） | プロトコル準拠、両トランスポート |
| JSON | Jackson | `rg --json` パース、ツール出力 |
| TOML | tomlj | 設定ファイルのパース |
| HTTP（単独利用） | 組込みサーブレットコンテナー（Jetty 等） | Streamable HTTP の配線 |
| CLI（単独利用） | picocli | `serve`／`sync` サブコマンド |
| ロギング | SLF4J ＋ Logback | 構造化ログ |
| Spring 統合 | Spring Boot ＋ MCP Java SDK の Spring 連携 | スターターの自動構成 |

ライブラリーの最終選定（特に TOML パーサーと組込みサーブレット
コンテナー）は、一次情報での確認のうえ実装初期フェーズで確定し、
該当する判断は ADR に記録する。

#### 6.3.3 ネットワーク

ネットワーク経由で Git リモートに到達可能であること。

### 6.4 リポジトリ規模の前提

- 1サーバーインスタンスが扱うリポジトリ数は50以下を想定する
- 1リポジトリあたりのサイズは5GB以下を想定する
- LLM 文脈の都合により、実運用上のリポジトリ数は5〜10程度が現実的である

### 6.5 公開ツールの方針

- 検索系ツールは `search_code`／`list_files`／`list_tree`／`read_file` の
  4つに限定し、加えて discovery 用の `list_repositories` を1つ公開する
- ツール名・パラメーター名は小文字スネークケースとする
- 自然言語応答や要約は本サーバーの責務としない

### 6.6 移植上の既知の差異

- **同期完了通知**: リファレンス実装は外部同期完了を `SIGHUP` で常駐
  サーバーへ通知する。JVM には標準のシグナル送受信 API が無いため、
  実現方式（非標準シグナル API の利用／OS シグナル受信／ファイル監視への
  置換）は ADR で判断する。
- **テストカバレッジ**: リファレンス実装は100パーセントを要求する。Java
  では JaCoCo で同等を狙うが、現実的な閾値は実装初期フェーズで確定する。

## 7. 用語定義

| 用語 | 定義 |
| --- | --- |
| MCP | Model Context Protocol。LLM クライアントが外部ツールにアクセスするためのプロトコル |
| MCP サーバー | MCP プロトコルでツールを公開するサーバー |
| MCP クライアント | MCP サーバーのツールを利用するクライアント |
| ツール | MCP プロトコルで公開される呼び出し可能な関数 |
| リポジトリ | 本サーバーで取り扱う単一の Git リポジトリ |
| 参照ブランチ | リポジトリごとに設定で指定された検索対象ブランチ |
| ワークスペース | 各リポジトリの clone 先となるサーバー上のローカルディレクトリ |
| ヒット | `search_code` で返される単一の一致箇所 |
| 単独利用 | CLI で起動するスタンドアロン実行形態 |
| Spring Boot 統合 | スターター経由で Spring Boot アプリへ組み込む形態 |
