# 設計

`docs/devel/design/`

要求・仕様をどのように実現するかを管理する。**現在有効な設計内容**のみを記述する。

「なぜその設計にしたか」という判断理由は ADR（`../adr/`）に記録する。

設計は観点ごとに分割されるため、必ずディレクトリとして管理する。`design.md`
単一ファイル運用は認めない。

## サブカテゴリ

- `architecture/` — システム全体構造、責務分割、依存関係、コンポーネント構成
- `application/` — アプリケーション内部設計、レイヤー、ユースケース、サービス
- `database/` — データモデル、テーブル設計、マイグレーション方針
- `interface/` — API、外部連携、ファイル連携、メッセージ連携
- `batch/` — バッチ、ジョブ、スケジュール、リトライ、排他制御

## 隣接カテゴリとの境界

- 採用した技術・方式の理由、代替案、判断の影響 → `../adr/`
- 何を満たせば正しいか → `../specs/`
- 実装規約（命名、ログ、例外等） → `../standards/`

## 相互参照

設計文書に関連 ADR がある場合、文書末尾に記載する:

```md
## Related ADRs

- ../adr/0003-adopt-flyway-for-db-migration.md
```
